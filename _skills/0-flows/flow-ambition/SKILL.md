# flow-ambition：一次提标，一张单子

## 这个 skill 做什么

altitude、deeper-not-bigger、assumption-audit、assemble-the-crew 原来各自停一次等你确认。这里让它们各自分析，合成一张提标单，你批一次，再按批示执行。每个方法的具体做法以它自己的 skill 为准。

“调 X”指用 Skill 工具加载 X 并照它做，同时遵守下面的总控协议。技能列表里的名字可能带前缀（例如 `anthropic-skills:altitude`），按名字找对应的那个。没有 Skill 工具时，直接读那个 skill 的 SKILL.md。

## 总控协议

1. **先看再问。** 开工前先查手上已有的：对话里的文件、记忆里的项目记录、已连接的应用、相关仓库、之前的批示文档。能查到的不问。
2. **一轮一张批示单。** 本轮所有要你拍板的事合成一张单子：逐条编号，每条写推荐和一句理由，你可以逐条批（采纳 / 改后采纳 / 暂缓 / 不做）。被调用的 skill 不再各自停下来问，它们要问的都并进这张单。4 条以内用提问工具，每条一问、推荐项放第一个；更多或要留档，用“逐条批示版”文档，每行一条、带“批示”下拉列；都没有就在对话里编号列出。
3. **原任务保底。** 你原来要的东西照交；提标和扩展只加不换。扩展不扩权限：发送、发布、删除、部署、合并、花钱、建定时任务，都先问。
4. **关口过独立核验。** 只在流水线里写了关口的地方做。派一个没看过过程的子 agent，只给它成品（需要时加原始材料），不给推理、设计说明和别人的意见；它回报成立 / 有洞 / 说不清，并写位置、原因、能否修。每条发现都归入已修、接受风险或需要你决定（并进下一张批示单），就算过关。没有子 agent，就交一段能直接粘贴进新会话的审查提示（只含成品和要查的清单）；这也做不到，就标“未经独立核验”，照常交付。
5. **没人在场时**（定时任务、你说晚点回来、单子半天没人批）：不用提问工具，批示单和进度写进逐条批示版文档（没有文档工具就写成 Markdown 文件）；开头写明取了哪种读法；按推荐项只做可逆的部分，项目最远做到“样本过关口”（学习、游戏类页面就是样本过独立试玩）。私有 Artifact 不算发布；推送到公开仓库、合并、删除、对外发送，都停在决定前。
6. **小任务直通。** 改动小、可逆、不新增页面或版本的事（修一个 bug、加一个按钮、一个快问题），不走流程：直接调对应的 skill 或直接做，结尾一句话说明可以走完整流程。
7. **记进度。** 跨轮或跨会话的工作，在批示文档末尾维护一张“进度”表（阶段 · 状态 · 下一步 · 卡在哪）；回来时先读它，从停下的地方接着做。
8. **环境不够就交接。** 跑不了代码、读不到数据或进不了仓库时，交一段能直接粘贴进 Claude Code 的提示：目标、材料在哪、方法、验证命令、完成标准。

## 三种用法

- **独立模式**（你直接说“往大了做 X”）：盘点 → 四个方法分析 → 提标单 → 执行。
- **嵌入模式**（flow-project 或 flow-research 调用）：做到提标单为止，把条目交回调用方，并进它的批示单；执行由调用方接着做。
- **小任务**：按协议第 6 条，不出提标单，原样做完，结尾一句话说可以往哪个方向提。

## 1 盘点与目标背后的目标

- 先看已有的（协议第 1 条），尤其是原始材料在哪、有没有能跑代码的环境。
- 写出你对“做完之后希望发生什么、谁拿它做什么决定”的推断，作为提标单的第 1 条让你确认。完全推断不出来时才问。

## 2 四个方法各自分析（都不单独停）

| 方法 | 什么时候跑 | 交到提标单上的 |
|---|---|---|
| altitude | 总是 | 四层阶梯；推荐层、它的裁判和首个探针 |
| deeper-not-bigger | 总是 | 四问的答案；目标及可查的依据；外部验证方式 |
| assumption-audit | 任务依赖一个默认结论，且手上有原始材料 | 待检验的命题、推翻判据、留出方案 |
| assemble-the-crew | 交付物要出彩，或明显卡在单一领域视角 | 团队（含红队）和每个角色要交的成果 |

依次调用：altitude 先定层，deeper-not-bigger 再定标准和裁判，然后按需 assumption-audit 和 assemble-the-crew。每个方法做到它“交给用户确认”的那一步为止，把要确认的内容带回来。

## 3 提标单

开头一句写原任务保底：“原来要的 ××× 照交。”然后一张表，按收益和成本排序，最多 7 条：

| 编号 | 升级 | 来自 | 成本（模型时间 + 你要提供什么） | 收益 | 裁判 | 推荐 |
|---|---|---|---|---|---|---|

- 第 1 条固定是“目标背后的目标”的确认。
- 每条都要有裁判，优先用工具、留出数据或真人。某条升级只能靠阅读来判断（例如幻灯片讲得清不清楚）时，可以用盲审子 agent 当裁判，标“模型盲审”，排在有硬裁判的条目之后。没有任何裁判的条目删掉，或标“未经外部验证”并排到最后。
- 出单的形式按协议第 2 条：提问工具、逐条批示版文档，或编号列表。

## 4 执行（独立模式）

- 只做批了“采纳”或“改后采纳”的条目，每个方法照它自己的执行步骤：altitude 做所选的层（第 4 层只出方案，同意后才建定时任务或实时页面）；deeper-not-bigger 先量基线、冻结裁判；assumption-audit 先封存留出集；assemble-the-crew 的红队盲审。
- 环境不够时，按协议第 8 条交一段 Claude Code 提示。
- 交付：原任务的成果、各条升级的成果，以及每条的“目标 vs 实测”和裁判结果。

## 例子

你说：“帮我把这季度的数字填进 QBR 模板。”

- 保底：模板照填。
- 提标单（节选）：
  1. 目标背后的目标：让管理层早发现问题，把钱和人调到对的地方（请确认）。
  2. altitude 推荐第 2 层：用全部数据解释变化，列出三个最紧迫的决策。裁判：下季度复盘这三个决策的结果。首个探针：用上季度数据试写一条“变了什么、为什么”，半小时内看能不能落到具体原因。
  3. assumption-audit：检验“流失主要是新手引导的问题”，留出最近一个季度。
  4. assemble-the-crew：分析师、调查记者、编辑，红队是卖空者。成本高，推荐暂缓。
