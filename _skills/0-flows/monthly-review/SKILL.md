# monthly-review：月度复盘

## 这个 skill 做什么

每月一次，分两步：

1. **出月报**：盘点本月做了什么，评判做得怎样（局部和整体），清理待决池，给 skill 建议、工作流差异和下月可选的三件事，合成一张批示单。
2. **批示后出存档**：把月报和你的批示合成一份结构固定的详细总结。以后每一期月报都从上一份存档读基线，你也可以按月调取。

日程（面试、截止日期、提醒）不归这里，另用日程工具；月报只在评判时引用已经发生的事。

“调 X”指用 Skill 工具加载 X 并照它做，同时遵守下面的总控协议。技能列表里的名字可能带前缀（例如 `anthropic-skills:reading-budget`），按名字找对应的那个。没有 Skill 工具时，直接读那个 skill 的 SKILL.md。

## 总控协议

1. **先看再问。** 开工前先查手上已有的：对话里的文件、记忆里的项目记录、已连接的应用、相关仓库、之前的批示文档。能查到的不问。
2. **一轮一张批示单。** 本轮所有要你拍板的事合成一张单子：逐条编号，每条写推荐和一句理由，你可以逐条批（采纳 / 改后采纳 / 暂缓 / 不做）。被调用的 skill 不再各自停下来问，它们要问的都并进这张单。4 条以内用提问工具，每条一问、推荐项放第一个；更多或要留档，用“逐条批示版”文档，每行一条、带“批示”下拉列；都没有就在对话里编号列出。
3. **原任务保底。** 你原来要的东西照交；提标和扩展只加不换。扩展不扩权限：发送、发布、删除、部署、合并、花钱、建定时任务，都先问。
4. **关口过独立核验。** 只在流水线里写了关口的地方做。派一个没看过过程的子 agent，只给它成品（需要时加原始材料），不给推理、设计说明和别人的意见；它回报成立 / 有洞 / 说不清，并写位置、原因、能否修。每条发现都归入已修、接受风险或需要你决定（并进下一张批示单），就算过关。没有子 agent，就交一段能直接粘贴进新会话的审查提示（只含成品和要查的清单）；这也做不到，就标“未经独立核验”，照常交付。
5. **没人在场时**（定时任务、你说晚点回来、单子半天没人批）：不用提问工具，批示单和进度写进逐条批示版文档（没有文档工具就写成 Markdown 文件）；开头写明取了哪种读法；按推荐项只做可逆的部分，项目最远做到“样本过关口”（学习、游戏类页面就是样本过独立试玩）。私有 Artifact 不算发布；推送到公开仓库、合并、删除、对外发送，都停在决定前。
6. **小任务直通。** 改动小、可逆、不新增页面或版本的事（修一个 bug、加一个按钮、一个快问题），不走流程：直接调对应的 skill 或直接做，结尾一句话说明可以走完整流程。
7. **记进度。** 跨轮或跨会话的工作，在批示文档末尾维护一张“进度”表（阶段 · 状态 · 下一步 · 卡在哪）；回来时先读它，从停下的地方接着做。
8. **环境不够就交接。** 跑不了代码、读不到数据或进不了仓库时，交一段能直接粘贴进 Claude Code 的提示：目标、材料在哪、方法、验证命令、完成标准。

## 时间窗口

- 日期一律按太平洋时间（America/Los_Angeles）取：用 current_time 工具，或在命令里设 `TZ=America/Los_Angeles`。会话时钟常是 UTC，太平洋时间周二傍晚在 UTC 已经是周三。
- 窗口从上一期窗口终点的第二天开始，到今天为止。上一期优先取存档；上一期只出了月报、没出存档（没批完），就取那份月报的窗口终点，并把“上期未存档”列进本期待决池。两样都没有时，从本月 1 日开始。
- 定时任务在每月最后一个周二触发，所以窗口不一定是整的自然月。月报第一行写明窗口起止日期；标题按窗口终点所在的月份命名，例如“月度复盘 · 2026-11”。
- 用户手动要月报时，按用户说的范围；没说就按上面的规则。

## 第一步：出月报

### 1. 收集（只读）

| 来源 | 怎么取 | 取什么 |
|---|---|---|
| 上一期存档或月报 | 按顺序找，找到就停：① 记忆里 `/areas/monthly-review.md` 的索引行（带链接和窗口）；② 当前目录或用户给的文件夹里的 `月度存档-*.md`；③ Artifact 的 list（mine，limit 50），找标题以“月度存档 ·”或“月度复盘 ·”开头的最新一份 | 上期窗口、指标基线、批了的改进和下月焦点、待决池现状 |
| 记忆 | memory_list，读窗口内更新过的 `/areas/`、`/topics/` 文件（多个路径一次读） | 项目、目标、决定、状态 |
| 主页仓库 | 匿名克隆 ZechenBian/ZechenBian.github.io，`git log --since --until`，数合并的 PR，统计改动最多的目录；读 `_skills/README.md` | 提交数、PR 数、改动方向、仓库里的 skill 清单 |
| 账户里的 skill | 技能列表（或 ListSkills） | 和仓库对比，找不同步的 |
| Artifact 与文档 | Artifact 的 list，筛窗口内更新的；读其中“逐条批示版”文档的批示列和进度表 | 批了什么、还没批什么、做到哪一步 |
| 过往对话 | 有搜索过往对话的工具就按项目名查；没有就在“要你核”里写明这一块看不到 | 没进记录的事 |

- 每条事实记住出处，月报里事实表的每行带来源。
- 不读邮件、日历等私人数据，除非用户在这次请求里点名要。
- 某个来源取不到（没有工具、没有权限、没有数据），就在“要你核”里写明哪一块没看到；不编造，也不用常识补。

### 2. 写月报

调 docs（Claude Docs）建文档“月度复盘 · YYYY-MM”；没有文档工具就写成 Markdown 文件。交付前调 reading-budget：顶块四行在最前面。第 2 节的深度是用户明确要的，不为预算删减，顶块写明这一节约几分钟。

结构固定，六节，顺序不变：

**§1 本月做了什么**

- 第一句带数字：多少个项目有动作、上线几个、搁置几个，提交和 PR 各多少。
- 一张表：方向 · 做了什么（带日期）· 状态（上线 / 建成未发布 / 样本 / 计划 / 搁置）· 来源。
- 和上期存档比，用一句话写变化最大的地方。

**§2 评判：局部和整体**（这是月报的核心）

局部：本月有动作的每个项目，写成一行或一小段。

- 想做到什么：取记录里用户自己说的目标。没有目标记录就写“未设目标”，这本身算一条不足。
- 实际做到什么。
- 不足：要具体、能指证。常见的有：停在 v0；没有真实使用者或外部反馈；没有测试或核验；范围在月内扩了几次；做了又搁置；和别的项目重复。
- 每条不足附证据，再写一条反方理由（这样做可能合理的原因）。反方理由也要有证据；有证据且站得住，这一条才降级为“观察”。

整体：

1. **投入分布。** 按本月数据自己归类（不套固定清单），统计每类的项目数、提交量和记录条数。写明这些都是代理指标，测不出真实花了多少时间。
2. **和长期方向对照。** 长期方向只取用户自己说过的（profile 和记录里的目标），并写出处，不替用户定方向。写出投入的大头和方向之间差多远，再和上期存档比，这个距离在拉大还是缩小。
3. **跨项目的模式。** 至少看四个问题：
    - 开了几个、收了几个：开始、完成、搁置的比例。
    - 产出还是验证：做出来的东西有没有被别人用过、有没有外部反馈。
    - 广度还是深度：每个项目推进到第几版。
    - 交给 Claude 的还是自己练的：关系到用户自己说过的学习目标。
    
    每个模式要有两条以上证据；只有一条证据的不算模式。
4. **最重要的一条不足。** 只挑一条，这一条不降级为“观察”。写四样：为什么是它（代价最大或拖累最多）；一条原因假设（为什么会这样）；下月怎么检验这个假设；下月用什么可数的指标看它有没有改善，例如“完成并发布的项目数”“有外部反馈的页面数”。
5. **上期改进项的回顾。** 上期存档里批过的改进，这个月的指标怎么样。第一期没有上期，写“无”。

写评判的规矩：

- 不奉承，不把“做了很多”本身当成就；也不说教。每个判断都要能被证据推翻。
- 事实和判断分开：表格放事实，判断单独成句，以“判断：”开头。
- 只评做事的方式，不评人格，不做心理推断。
- 不往用户的专业领域上拉；对照方向只用用户自己说过的目标。
- 改进建议编号 P1、P2……进批示单。

**§3 待决池**（未答复的批示、搁置的项目、暂缓的改动、建成未发布的东西、计划了没开工的，合在一张表里）

- 列：编号 D1…… · 事项 · 类型 · 从哪天起 · 条件变了吗（一句事实）· 推荐（继续搁置 / 拿出来做 / 放弃 / 要你定）。
- 条件没变就推荐继续搁置，不每月催。连续三期都是“继续搁置”的，推荐一次“放弃，或写明重启条件”。
- 上期存档里的待决池逐条带过来；本月新增的标“新”。

**§4 Skill 体检与建议**（只出建议，不动手）

- 同步：仓库 `_skills/` 和账户技能列表的差异。
- 挖掘：窗口内同一种做法出现两次以上、现有 skill 都管不到的，作为候选。每个候选写：证据（带日期）、GitHub 上最接近的公开 skill（用 WebSearch 找，打开页面后再写；没读到 SKILL.md 全文的标“未细读”；没有搜索工具就标“未查外部”）、差在哪、建议（新建 / 并入某个 skill / 借用外部 / 暂缓）。编号 S1、S2……
- 以前否决或暂缓过的候选不重提，除非证据有新增，并写明新增了什么。
- 不写 skill、不开 PR、不出保存卡片。用户批了要做，另开一轮用 skill-creator 做。

**§5 工作流改动**

- 只写和上期相比要改的地方，编号 W1、W2……；没有就写“无”。

**§6 下月可选的三件事**

- F1–F3，每条写做什么、对应 §2 的哪条不足或 §3 的哪一项、下月怎么判断做成了。三条可以全不采纳。

**批示单**：P、D、S、W、F 各条按协议第 2 条合成一张单。条目多于 4 条时，月报本身就是逐条批示版：每张表带一列“批示”下拉（采纳 / 改后采纳 / 暂缓 / 不做），用户也可以在条目下评论。

### 3. 关口：独立核验

交付前派一个子 agent，只给它月报和第 1 步收集到的材料清单，让它查四件事：每条事实有没有来源；§2 的每条不足有没有证据；窗口内更新过的项目记录有没有漏进月报；§2 里有没有空话，即无法被证据推翻的句子和夸奖用语（如“有待加强”“很有成效”“成果丰硕”），有就改成具体的事实和判断。结果按协议第 4 条处理。

## 第二步：批示后出存档

触发：用户批完了，在文档的批示列填完，或在对话里说“批完了”“出存档”。

- 读月报的最新版，包括批示列和评论。没批的条目记“未批”，不替用户批。
- 新建 Docs 文档“月度存档 · YYYY-MM”（没有文档工具就写成 Markdown 文件）。存档的结构各期相同，名字和顺序都不改，方便对比和检索：
  1. **三行摘要**：本月一句话、最大的不足、下月焦点。
  2. **元信息**：窗口起止、月报链接、批示日期。
  3. **本月事实**：§1 表的定稿，不改写事实。
  4. **评判定稿**：局部和整体的结论按批示调整后的版本。用户在批示或评论里反驳的，写“用户意见”，同时保留原判断和理由。
  5. **决定台账**：每条一行，编号 · 事项 · 批示 · 用户备注，暂缓和不做的也记。
  6. **待决池现状**：批完后每条的状态和计数（已经连续搁置几期）。
  7. **下月焦点与指标**：批了的 F 条，加上 §2 第 4 条的指标，写成下期能直接对照的数字基线。
  8. **指标基线**：本月的代理指标数字（有动作的项目数、上线数、搁置数、提交、PR、skill 数等），供下期 §2 看趋势。
- 存档是给以后的月报和以后的你读的，要写全，不受阅读预算的正文上限；只有最上面的三行摘要要短。
- 有记忆工具时，在 `/areas/monthly-review.md` 加一行索引：月份 · 窗口起止 · 存档链接 · 批了的下月焦点。文件不存在就新建。没有文档工具时，存档文件名用 `月度存档-YYYY-MM.md`，下期按这个名字找。
- 调取：用户问“前几个月……”时，列出各期存档，按需读取后回答，答案标明出自哪一期。

## 定时运行

- 定时任务的写法：`CRON_TZ=America/Los_Angeles` 下每周二 17:00 前后运行一次（cron 里同时限定日期和星期时取“或”，所以不能写成“25–31 日的周二”，只能每周跑、再自己判断）。建或改这个定时任务要先问用户（协议第 3 条）。
- 每次运行先按太平洋时间取今天的日期，判断是不是本月最后一个周二：今天加 7 天如果落到下个月就是。不是就直接结束，不出文档、不发通知。
- 是最后一个周二：先查这个窗口是否已经出过月报（用户月中手动要过）。出过就不再新建，只在那份月报末尾补上之后几天的新动作。
- 没人在场（协议第 5 条）：只做第一步，出月报文档，结尾发一条推送通知说月报好了；发不了通知，就在月报顶块写“应发通知，未发出”。不出存档、不建 skill、不开 PR、不改记忆、不改仓库。

## 什么时候不用

- “今天做了什么”“这周进展”这类快问题：直接回答。
- 日程、提醒、截止日期：用日程工具。
- 只想把一份已有的长文读快一点：用 read-for-me。
