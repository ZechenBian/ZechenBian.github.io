# flow-project：项目从想法到上线

## 这个 skill 做什么

把评估、提标、样本、铺开、合并串成一条流水线。它只管三件事：**顺序**、**每轮只问一次**、**每个关口过独立核验**。每一步具体怎么做，以被调用的 skill 为准，这里不重复。

“调 X”指用 Skill 工具加载 X 并照它做，同时遵守下面的总控协议。技能列表里的名字可能带前缀（例如 `anthropic-skills:lab-builder`），按名字找对应的那个。没有 Skill 工具时，直接读那个 skill 的 SKILL.md。

## 总控协议

1. **先看再问。** 开工前先查手上已有的：对话里的文件、记忆里的项目记录、已连接的应用、相关仓库、之前的批示文档。能查到的不问。
2. **一轮一张批示单。** 本轮所有要你拍板的事合成一张单子：逐条编号，每条写推荐和一句理由，你可以逐条批（采纳 / 改后采纳 / 暂缓 / 不做）。被调用的 skill 不再各自停下来问，它们要问的都并进这张单。4 条以内用提问工具，每条一问、推荐项放第一个；更多或要留档，用“逐条批示版”文档，每行一条、带“批示”下拉列；都没有就在对话里编号列出。
3. **原任务保底。** 你原来要的东西照交；提标和扩展只加不换。扩展不扩权限：发送、发布、删除、部署、合并、花钱、建定时任务，都先问。
4. **关口过独立核验。** 只在流水线里写了关口的地方做。派一个没看过过程的子 agent，只给它成品（需要时加原始材料），不给推理、设计说明和别人的意见；它回报成立 / 有洞 / 说不清，并写位置、原因、能否修。每条发现都归入已修、接受风险或需要你决定（并进下一张批示单），就算过关。没有子 agent，就交一段能直接粘贴进新会话的审查提示（只含成品和要查的清单）；这也做不到，就标“未经独立核验”，照常交付。
5. **没人在场时**（定时任务、你说晚点回来、单子半天没人批）：不用提问工具，批示单和进度写进逐条批示版文档（没有文档工具就写成 Markdown 文件）；开头写明取了哪种读法；按推荐项只做可逆的部分，项目最远做到“样本过关口”（学习、游戏类页面就是样本过独立试玩）。私有 Artifact 不算发布；推送到公开仓库、合并、删除、对外发送，都停在决定前。
6. **小任务直通。** 改动小、可逆、不新增页面或版本的事（修一个 bug、加一个按钮、一个快问题），不走流程：直接调对应的 skill 或直接做，结尾一句话说明可以走完整流程。
7. **记进度。** 跨轮或跨会话的工作，在批示文档末尾维护一张“进度”表（阶段 · 状态 · 下一步 · 卡在哪）；回来时先读它，从停下的地方接着做。
8. **环境不够就交接。** 跑不了代码、读不到数据或进不了仓库时，交一段能直接粘贴进 Claude Code 的提示：目标、材料在哪、方法、验证命令、完成标准。

## 流水线

| 阶段 | 调用 | 关口（过了才进下一阶段） |
|---|---|---|
| 0 盘点 | — | 知道从哪一阶段接着做 |
| 1 评估 | kickoff-assessment | 你在批示单上选 A（做样本） |
| 2 提标（可选） | flow-ambition 的嵌入模式 | 你批定层级、目标和裁判 |
| 3 样本 | 学习、游戏类页面：lab-builder；其他项目：评估里定的最小样本 | 学习、游戏类：独立试玩，没看过设计的人只玩页面，说得出设计目标；其他：评估或提标里定的裁判 |
| 4 铺开 | 学习、游戏类：lab-builder 的铺开规则；其他：按评估里的分期 | 抽查：独立审查者对照样本规则抽查 3 个条目 |
| 5 合并 | 学习、游戏类：lab-builder 的交付前检查；都要遵守项目所在仓库的 CLAUDE.md | 自动检查全绿，并且你说“合并” |

### 0 盘点（每次进入都做）

- 读已有的：对话里的文件、记忆里的项目记录、批示文档的进度表。页面类项目把 ZechenBian/ZechenBian.github.io 挂进会话，读它的 CLAUDE.md 和相关目录。
- 判断从哪一阶段接着做：已有评估就不重做；已经决定要做的项目从阶段 3 开始；已有样本就从样本的关口开始。

### 1 评估

- 调 kickoff-assessment 出评估。它结尾的 A / B / C 是本轮批示单的第一条；“头号假设”的最小验证如果能放进样本里做，写成单上的一条。
- 你说“攻击它”时用它的压力测试模式；攻击结束前不进阶段 2。
- 选 B：按批示改方案，回到本阶段。选 C：在进度表上记“已放弃”和原因，结束。

### 2 提标（可选）

- 推荐做的情形：要公开推广、要拿去展示，或你说“做到最好”。纯自用的小东西默认跳过，把“建议跳过提标”作为一条放上批示单让你确认。
- 调 flow-ambition 的嵌入模式：它只交提标单的条目，并进本轮批示单，不单独停。
- 批示后，把选定的层级、目标、裁判、团队和检验条目写回任务描述，交给阶段 3。评估里定的最小样本照做（原任务保底）。批了的检验条目（assumption-audit）在阶段 3 按批过的方案做；团队和红队在样本做完之后上场。

### 3 样本

- 学习、游戏类页面：lab-builder 的“样本”步骤，含它的独立试玩。其他项目（agent、工具、脚本、与学习和游戏无关的页面）：做评估里定的最小样本，用阶段 2 定的裁判检验；没有提标，就用评估里的放弃条件检验。凡是页面，样本都另发一份私有 Artifact，方便你直接试玩（分支在 GitHub Pages 上没有网址）。
- 关口：试玩结果或裁判结果，和样本的私有 Artifact 链接一起放上批示单。试了两轮仍说不出设计目标，就把这件事放上批示单，由你决定改设计还是照样往下走。

### 4 铺开

- 用 lab-builder 的铺开规则（其他项目同样适用）：先把样本为什么好写成 3–5 条规则放进文件头，后面的条目照着做。其他项目铺开的范围按评估里的分期。
- 关口（抽查）：派一个独立审查者，只给它样本规则和随机抽的 3 个条目，逐条判断是否符合；不符合的条目回炉。

### 5 合并

- 学习、游戏类过 lab-builder 的交付前检查；所有项目都按所在仓库的 CLAUDE.md 开分支、写 PR 说明、在本地跑检查。不放进仓库的项目（例如只发成 Artifact 的工具），发布同样等你点头。
- 只有你说“合并”才合并。合并后在进度表上记网址和版本。

## 批示单示例（阶段 1 结束时）

| 编号 | 事项 | 推荐 | 理由 |
|---|---|---|---|
| 1 | 做不做样本（A / B / C） | A | 核心循环清楚，头号假设能在第一关里验证 |
| 2 | 头号假设“玩家愿意自己推出规律”的验证 | 放进样本 | 不额外花时间 |
| 3 | 提标 | 跳过 | 先自用，看过样本再说 |

## 什么时候不用

- 只要评估、还不打算走流程：直接用 kickoff-assessment。
- 给已有实验室加一个小功能、修一个 bug：直接用 lab-builder（协议第 6 条）。
