# 实验室建造规程

## 这个 skill 解决什么

用户已经用同一种形态做了十来个浏览器实验室。这份规程把那套形态、流程和质量标准固定下来：一是不用每次重新解释，二是避免"第一版能跑"就交付——用户审的是手感，不是骨架。

前置评估（可玩性、独立还是并入）按 `kickoff-assessment` 的结构做；用户说"先评估 / 先别建"时只评估、不写代码。整条流程（评估 → 提标 → 样本 → 铺开 → 合并）由 `flow-project` 编排时，本 skill 每一步结束的确认并进它的批示单。

**分工**：这个 skill 管实验室怎么设计、怎么教、怎么审；仓库的工程规矩（源码放哪、怎么构建、怎么开分支和 PR、自动检查）写在主页仓库根目录的 `CLAUDE.md`，以它为准。动仓库之前先读 `CLAUDE.md`。

**仓库不在会话里时**：先把 `ZechenBian/ZechenBian.github.io` 挂进会话（有挂仓库的工具就用），再读 `CLAUDE.md`。挂不上就说明原因，这一轮只做单文件样本（用 Artifact 发布），等仓库可用了再按规矩入库。

## 形态约定

- **交付形态是单文件页面**：每个实验室（或它的一个版本）发布出去是一个自包含的 `index.html`，HTML/CSS/JS 全部内联。原因：仓库是 GitHub Pages，服务器上不跑构建；单文件便于直接发链接、断网也能打开。
- **源码在仓库里，构建出单文件**：稍大的项目把源码拆在项目的 `src/` 里，由项目自己的构建脚本（`build.py` 或 `build.js`，不用框架和打包器）拼成单文件；源码和构建产物放在同一个提交里。很小的页面可以直接手写单文件。不在仓库外的目录开发再复制进来。
- **位置**：主页仓库 `ZechenBian.github.io` 的子目录，例如 `strategy-lab/`、`strategy-lab/teen/`、`strategy-lab/ml/`、`strategy-lab/cases/`、`tianxia-v3/`。资源一律相对路径。新页面登记到 `.github/scripts/pages.json`，构建出来的页面还要加进 `.gitattributes`（见 `CLAUDE.md`）。
- **版本**：新的大版本**不复制目录**，而是用开关或配置从同一份源码构建出来，新版本放在新网址，旧网址保持可玩。共享代码的改动会进入所有版本：在 PR 说明里逐个列出每个版本是否受影响；只想改新版就加开关。确实需要复制才能做的，先停下来问用户。
- **依赖**：只从 CDN 加载（优先 cdnjs），其余内联；断网也要能打开页面主体（自动的冒烟测试会切断外网打开每个页面）。
- **手机**：手机宽度可用，无横向滚动；localStorage 只做便利（进度、偏好），读写包 try/catch，缺失时页面照常渲染。
- **页脚**：© Zechen Bian · All rights reserved（公开但不开源）。
- **私密信息**：API key、密码一律不写进页面；需要 key 的功能给输入框，由使用者自己填。

## 流程：评估 → 样本 → 铺开 → 合并

每一步结束都停下来等用户确认（由 flow-project 编排时并进它的批示单；没人在场时见下文）。用户没说"直接合并"，就不合并。

1. **评估**：可玩性、技术可行性、独立页面还是并入已有实验室。结构见 `kickoff-assessment`。
2. **样本**：先做最小可审的一块（诺奖站先做 10 个奖、文学奖和和平奖先做、思想实验室先做轴心时代一段、十关谜题先做一关）。样本要做到"能完整玩一遍"的完成度。交给用户审之前，先过下面的**独立试玩**。
3. **铺开**：铺开之前，把"样本为什么好"写成 3–5 条规则放在文件头部注释里，后面的条目照着做。原因：50 个平庸条目不如 5 个好条目，规则写下来才不会在第 30 个条目时走样。
4. **合并**：过一遍下面的交付前检查，再按 `CLAUDE.md` 开分支、开 PR。

## 独立试玩（样本的关口）

样本做得好不好，最后看的是一个没看过设计的人能不能自己玩出设计想让他发现的东西。

- 样本做完、交给用户审之前，派一个没看过设计的新子 agent（或请一位真人），只给它页面（链接或文件），只说"把它玩一遍"。不给设计文档、目标结论、玩法提示，也不说你希望它发现什么。
- 子 agent 用浏览器工具或 Playwright 实际操作，手机宽度和电脑宽度各玩一次，回报三件事：这个页面想让我发现或学会什么；我在哪一步卡住、为什么；哪一步不知道该干什么。
- 判定：它说出的结论和设计目标一致 → 通过。不一致或说不出 → "重新发现"没有成立：先改样本（改引导、反馈和关卡顺序，不是加说明文字），再试一次。
- 它说了什么、卡在哪、你改了什么，原样附在交给用户的样本说明里。没有子 agent 就开新会话或请真人；都做不到，就标"未经独立试玩"。

## 内容与教学风格

- **重新发现式**：先给现象、数据或当年真实的困难，让玩家自己重建结论；公式和叙述放在玩家尝试之后。用户明确把诺奖站从"讲解"改成了"重新发现谜题"，这是所有知识类实验室的默认。
- **开头一页总览**：研究这个问题需要什么、各理论为什么冲突、这个实验室打算让你看到什么。
- **青少年版**（单独目录、中文）：先手玩一局再讲原理；补编程与算法的基本思想；例子更多更简单，解释更细。
- **宁缺毋滥**：跳过站不住脚或有重大伦理争议的条目。
- **争议内容**：中性表述，多方立场并列，不下结论。

## 数据与引擎

- **每个数据集标注"模拟 / 真实"**，标签放在数据旁边，不只写在说明页。原因：混淆会让结论失效，用户明确要求过。
- 真实数据优先。按用户描述从网上取数时：先找来源，记录 URL、许可和取数日期，一并写进页面。
- **本地 Python 引擎**可选：页面提供"连接本地引擎"的入口，不连接时功能完整。
- **页内 AI 引擎**：需要 AI 判定或生成时，优先用 Artifact 的运行时能力；在 GitHub Pages 上则由使用者自填 key。

## 语言与多人

- 默认中文；重要页面提供英文版并可一键切换。两种语言的内容必须一致——新增条目两边都加。
- 联机 / 多人：每个玩家用自己的语言收到反馈；导出到 GitHub 后同学凭链接直接玩。

## 交付前检查（开 PR 前逐条过）

1. 自己打开页面从头玩一遍（用浏览器工具），列出 bug 和卡点，修完再交。
2. 在本地跑仓库的自动检查（`CLAUDE.md` 里列的规矩检查、重建一致、冒烟测试，以及该项目自己的测试），全绿再开 PR。冒烟测试管控制台报错和手机宽度横向滚动，但不替代第 1 条的亲手试玩。
3. 样本阶段的独立试玩结果附在 PR 说明的"怎么验证的"里。
4. 所有数据集有"模拟 / 真实"标签；真实数据有来源。
5. 有英文版的，中英内容一致。
6. 页脚版权声明在；旧网址仍然可玩；PR 说明里逐个列出每个版本受不受影响。
7. 要在中国大陆推广的内容，按中国标准审查：地图与地名、涉华表述、真实机构名加免责声明、删除不当选项。审查结果单独列给用户看，并写明每个版本各自是否生效。
8. 主页索引（如有）加上新页面链接；新页面登记到 `.github/scripts/pages.json`。

## 合并

用户说"合并"才合并。按 `CLAUDE.md`：一个分支、一个 PR 只做一件事，PR 说明写清改了什么、为什么、影响哪些页面和版本、怎么验证的（附截图）；自动检查"全部检查"通过才能合并。

## 没人在场时

定时任务里，或用户说晚点再看：按推荐项推进到下一个停点——评估、样本、独立试玩、在分支上提交都可以做；合并、发布、删除不做。开头写明按哪种理解推进的。

## 推广类问题

用户问"怎么推广 / 给谁用 / 先改什么"时：先给目标受众（具体人群与场景），再给三个优先改进项（按对该人群的影响排序），最后给渠道。不要泛泛而谈。

## 不要做的

- 用户说"先评估"时写代码。
- 为了铺开数量牺牲样本质量。
- 引入框架、打包器（webpack、vite 之类）或服务器；项目自己的简单构建脚本可以。
- 复制目录做新版本。
- 直接手改构建出来的页面。
- 把 key 或私密数据写进页面。
