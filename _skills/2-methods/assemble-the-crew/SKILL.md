# assemble-the-crew：组建跨领域团队

来源：Felix Rieseberg《How to be more ambitious》中的「广度」。过去请多个领域的人一起看同一件事成本太高，现在可以用多个子智能体做到。最大的风险是变成角色扮演：让模型模仿专家的口吻，而不是去做专家实际会做的事。

## 何时用

- 交付物需要做得出彩：演示、发布、重要文档、产品或视觉设计。
- 用户觉得结果平庸，或者明显只用了一个领域的视角。

不用：边界清楚、单一领域就能做好的事。

## 与其他 skill 的关系

- **排在最后**：先用 altitude 选层、deeper-not-bigger 定标准，再按动词组队。
- **让给**：单一领域就能做好 → deeper-not-bigger。
- **一轮只停一次**：单独使用时只在第 3 步停一次（团队设计）。
- **由 flow 编排时**：第 3 步的团队设计并进它的批示单，不单独停。
- **小任务**：按上面“不用”的情形，不组队，直接做。

## 流程

### 第 1 步：把名词改写成动词

把任务里的名词（「一份幻灯片」「一个网站」）改写成它实际要完成的动作，写 1 到 3 句。例如，季度回顾不是「一份幻灯片」，而是「让忙碌的人在半小时内相信一个因果故事，并在不确定中做出决策」。

### 第 2 步：按动词找领域

对每个动词问：哪个领域最擅长做这件事？把候选领域都列出来，包括不太显然的领域。

### 第 3 步：团队设计，交给用户决定（开工前）

按「如果做砸了后果极其严重，人类会派谁上」的思路挑选成员，给出一份团队设计：

- 成员数量和每个角色（按任务而定，不设固定规模）。
- 至少一个红队角色，专门找漏洞，例如卖空者、审计、对手方。
- 每个角色实际会做什么、用什么方法、交出什么成果。
- 执行方式：重要任务并行派出子智能体，一般任务在一个会话里依次完成；说明大致的用量。

然后停下，等用户增删角色或确认。

### 第 4 步：执行

- 每个角色交一份工作成果：分析、数据、修改稿、测试结果或反对意见清单。
- 硬规则：不写「以某某身份发言」的段落，不模仿口吻。检验标准：去掉角色名之后，这份产出仍然是有用的工作成果。
- 当前环境做不了某个角色需要的工作（如渲染、数据分析）时，给出一段可以直接粘贴进 Claude Code 的实现提示。
- **红队最后上场，盲审。** 红队只拿整合后的成品和原始材料，不拿其他角色的理由、讨论和你的取舍。有多个红队成员时各自独立审，互不看结论。没有子智能体时，交一段能直接粘贴进新会话的红队审查提示（只含成品、原始材料和要找的漏洞类型）；都做不到，就标「红队未盲审」。

### 第 5 步：汇总

- 列出各角色之间的冲突和取舍，说明采纳了谁的意见、为什么。
- 红队的问题先去重：同一处的同一个问题合并，记下有几个人提了。再按 **致命 / 重要 / 一般** 排序，逐条标明：已修复、接受风险，还是需要用户决定。
- 交出整合后的最终产物。

## 没人在场时

按推荐的团队设计，在一个会话里依次完成各角色，不并行派子智能体；红队盲审照做（派一个子智能体，只给成品和原始材料）。开头写明按哪个设计推进；对外发送和发布停在决定前。

## 示例

任务：「做一份季度业务回顾。」

- 动词：让忙碌的人在半小时内相信一个因果故事，并在不确定中做决策。
- 团队设计：数据分析师（从原始数据找出变化及其原因）、调查记者（把因果讲成可信的故事并核实）、编辑（压缩到半小时能读完）；如果要现场演示，再加动效和音频设计；红队是卖空者（找最容易被看空的数字）和法务会计（检查数字口径）。
- 等用户确认后再开工。红队拿到的是整合后的回顾和原始数据，看不到分析师的推理。

## 常见失败

- 角色扮演：产出只是换了口吻。
- 团队成员都来自相近的领域。
- 没有红队，或者红队的意见在汇总时被悄悄忽略。
- 红队看了其他角色的理由，审成了附和。
- 未经用户确认就并行派出大量子智能体。
