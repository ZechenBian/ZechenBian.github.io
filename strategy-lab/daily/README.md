# 每日一题：题目的接口 · Daily challenge: the content interface

**In English, briefly.** A daily challenge is one JSON file, `q/<UTC date>.json`: a small game with a referee, a few reference rules, starter code, and the number of data sets. The page fetches these files at run time, so adding challenges needs no rebuild: once they are merged into `main` and GitHub Pages has deployed, they are live. `node daily/check.js` validates a file by running it in exactly the program the page runs. The rest of this document (in Chinese) gives the file format, the standard a challenge has to meet, and the weekly procedure for writing and reviewing a batch.

每日一题的题目是数据，不随页面发布：页面运行的时候按日期去取 `daily/q/日期.json`。所以加题不用重新构建，合并进 `main`、GitHub Pages 发布完就上线。这份文档写四件事：一天是怎么过的、题目文件的格式、一道题要达到的标准、每周出题和送审的流程。

```
daily/
├── README.md          这份文档
├── check.js           校验脚本（只用 Node 自带的模块）
├── index.json         有题的日子的清单，由 check.js --index 生成，不要手写
└── q/2026-10-14.json  一天一个文件，文件名就是日期（UTC）
```

## 一天是怎么过的

日期一律按 UTC 算。

| 时刻（UTC） | 北京 | 加州 | 发生什么 |
|---|---|---|---|
| 0 点 | 早上 8 点 | 前一天 17 点（冬令时 16 点） | 这一天的题开放。题目自带"公开的几组数据"，谁都可以拿自己的规则去试，试几次都行 |
| 24 点 | 第二天早上 8 点 | 17 点（冬令时 16 点） | 截止。交规则就是在本仓库贴一条 Issue；同一个账号只算截止前最后交的那一条 |
| 24 点过 30 秒 | | | 公共随机信标 drand 发布这一轮的随机数，"结算的几组数据"由它定下来。之后谁打开往期的榜，谁的浏览器就把所有交上来的规则在这几组上重跑一遍，排出名次 |

- 一组数据 = 一个种子发出来的 K 局。每一局发给每条规则的是同一副牌，所以规则之间的差别不是牌运。
- 公开的几组，种子由日期、题目的指纹和 `sets.seed` 算出来，谁都能算。结算的几组，种子还要加上 drand 那一轮的随机数：截止之前没有人算得出来，截止之后人人取到的是同一个数，所以每个人排出来的是同一张榜。
- **没有题的日子**（清单里没有这一天）：页面按日期从以前的题里固定挑一道重温，公开的和结算的数据都是新的，榜也是这一天自己的。所以哪一周没来得及出题，页面不会空着。
- **已经开始的日子不能再加题、换题**。交上来的规则带着题目的指纹（裁判的代码、`T`、`p`、`sets`、`higher` 合起来算的），指纹对不上的不算；中途换题，当天已经交的人就白交了，写到一半的草稿也会被换掉。改错别字、改注释、改基准规则不影响指纹，随时可以改。

## 一道题的格式

| 字段 | 必填 | 内容 |
|---|---|---|
| `v` | ✓ | 固定写 1 |
| `day` | ✓ | 日期（UTC），和文件名一致 |
| `id` | ✓ | 这道题的代号：小写字母、数字、连字符，2 到 40 个字符。整个仓库里不能重复 |
| `title` | ✓ | 题目的名字，不超过 60 个字 |
| `summary` | ✓ | 一句话说这道题难在哪儿，不超过 200 个字 |
| `about` | ✓ | 题面，不超过 6000 个字 |
| `note` | | 补充的话：已经知道的理论、这道题难在哪儿。可以不写 |
| `T` | ✓ | 一局最多几回合，1 到 2000 |
| `p` | | 题目的参数，最多 12 个；名字用字母，值是有限的数。裁判里是 `deal` 的第三个参数，规则里用 `s.g` 读 |
| `code` | ✓ | 裁判的代码：必须有 `deal` 和 `referee`，可以有 `show` |
| `sets.pub`、`sets.fin` | ✓ | 公开的数据几组、结算的数据几组，各 1 到 40。一般都写 10；局数少、一局很长的题可以少几组，噪声大的题可以多几组 |
| `sets.K` | ✓ | 每组几局，1 到 5000 |
| `sets.seed` | ✓ | 公开那几组的种子从它来：0 到 2147483647 的整数。习惯上写成日期，比如 20261014 |
| `higher` | | 分数越高越好写 `true`（不写就是它），越低越好写 `false` |
| `digits` | | 成绩显示几位小数，0 到 6，不写是 3。选到标准误至少看得出一位有效数字 |
| `refs` | ✓ | 基准规则，2 到 6 条。第一条是"基准"：榜上"比基准多"那一列是和它逐局相减 |
| `refs[].id`、`name`、`summary`、`p`、`code` | ✓ | 代号（这道题里不重复）、名字、一句话说明、参数、代码（必须有 `decide`） |
| `starter.p`、`starter.code` | ✓ | 起始代码和它的参数：打开题目时编辑框里放的就是它 |

计算量有上限：`max(sets.pub, sets.fin) × sets.K × T` 不超过 200 万。

**文字**（`title`、`summary`、`about`、`note`、基准规则的 `name` 和 `summary`）都写成 `{ "zh": …, "en": … }` 两份。每一份可以是一个字符串，也可以是"一行一个字符串"的数组（改动好审，推荐）。英文那一份里不能有汉字和全角标点。

`about` 和 `note` 按手册的排版规则来排，能用的写法：空行分段、`**加粗**`、`*斜体*`、`` `行内代码` ``、`-` 开头的列表、`1.` 开头的列表、表格、`$…$` 里的公式（KaTeX）。两个 `$` 之间的字会被当成公式，所以写钱数不要用 `$`。

**代码**（`code`、`refs[].code`、`starter.code`）：

- 只许有整行的 `//` 注释，不许有 `/* */` 和反引号。页面执行的是去掉注释以后的那一份。
- 有注释的代码也写成 `{ "zh": …, "en": … }` 两份，两份去掉注释以后必须一字不差（所以两种语言的页面跑的是同一段代码，报错的行号也一样）。没有注释、全是 ASCII 的代码可以只写一份。
- 不许出现：`eval`、`Function`、`import`、`require`、`fetch`、`XMLHttpRequest`、`WebSocket`、`importScripts`、`postMessage`、`globalThis`、`self`、`window`、`document`、`Date`、`setTimeout`、`setInterval`、`performance`、`Math.random`。变量也不要起这些名字。
- 结果必须可复现：同样的种子跑两遍，一个数都不能差。

### 裁判：三个函数

```js
// 发牌。每一局开始时调用一次，返回这一局藏起来的东西 G（一个对象）。规则看不到 G。
function deal(T, rng, p) { … }
// 亮牌。每回合开始时调用，返回规则这一回合看得到的东西。可以不写（规则看到的就是 NaN）。
function show(G, t) { … }
// 判分。规则报出一个数 a 之后调用，返回这一回合的得分（必须是有限的数）。可以在 G 上记账；把 G.over 设成 true，这一局到此为止。
function referee(G, t, a) { … }
```

- 一局的得分是各回合得分加起来；成绩是所有局的平均。
- 随机数只能从 `rng` 来：`rng.u()`（0 到 1 均匀）、`rng.uniform(lo, hi)`、`rng.normal(mean, sd)`（不写参数是标准正态）、`rng.exp(rate)`、`rng.bernoulli(p)`、`rng.int(n)`、`rng.choice(arr)`、`rng.poisson(lam)`、`rng.gamma(k)`、`rng.t(nu)`、`rng.laplace()`、`rng.cauchy()`。`show` 和 `referee` 拿不到 `rng`：这一局要用的随机数在 `deal` 里一次抽好，存进 G。这样每条规则面对的才是同一副牌。
- `show` 可以返回一个数、一个数组（最多 256 个数），或者只有一层的对象（最多 32 个字段，字段的值是数或者数组）。嵌套的对象规则看到的是 NaN。
- 规则报什么数都有可能：负数、小数、极大的数；报的不是有限的数时，`referee` 收到的 `a` 是 NaN。`referee` 对任何 `a` 都要返回有限的数，不能抛错、不能死循环。该怎么处理不合规矩的报数（当成 0、当成不动……），在题面里写明。

### 规则：大家写的东西

```js
function init(p) { … }           // 可以没有。每一局开始时调用一次，返回的对象就是下面的 st
function decide(s, p, st) { … }  // 必须有。每回合调用一次，返回一个数
```

`s.see` 是 `show` 给的东西；`s.t`、`s.T` 是第几回合（从 0 起）和一局最多几回合；`s.last` 是上一回合的得分（第一回合是 NaN）；`s.total` 是这一局到目前的得分；`s.g` 是题目的参数；`s.rnd()` 给一个 0 到 1 的随机数。`p` 是这条规则自己的参数，`st` 是它在一局之内的记事本。

## 一道题要达到的标准

校验脚本管得了的（不过就不能送审）：

1. 格式对，中、英两份齐全，代码没有语法错误，起始代码的两份一样。
2. 裁判、基准规则、起始代码放进和页面一模一样的程序里跑得通，没有报错，没有"报的不是数"的回合。
3. 可复现。
4. 分得出高下：至少有一条基准规则和"基准"在公开的几组上逐局相减，差别超过 3 个标准误。
5. 不慢：一条规则跑完公开的几组不超过 4 秒。
6. 裁判受得了乱报的数：脚本会放几条乱报数的规则上去（不是数、极大的正负数、小数、范围外的整数），裁判都得回一个有限的数。

校验脚本管不了、要出题的人自己保证的：

1. **是一个要在不确定的情况下做决定的问题**，得分的算法说得清。不要求有确切的最优解，但要有东西可想：最朴素的做法是什么，稍微动动脑子能好多少，再往上难在哪儿。
2. **题面自己就说得清**，不用看代码也能动手写规则。必须写明三样：规则每一回合看到的是什么（`s.see` 的每个字段），报的数代表什么（不合规矩的数怎么处理），怎么得分。数字都写具体的。
3. **题面里的每一个数、每一句断言都要和裁判的代码对得上**：回合数、参数、分布、边界情况。`note` 里引用的理论值要么能推出来，要么用大样本核对过；核对不了的不要写。
4. **基准规则留有余地**。第一条（基准）是最朴素的做法；后面的一两条是看得出道理的改进，但不要把最好的办法放进去。出题的时候另外写一条更强的规则，用 `--try` 试，确认它在换过的数据上比最好的基准规则好出 3 个标准误以上；这条规则不放进题目，也不贴出来。
5. **起始代码**拿来就能跑，最好就是其中一条基准规则；开头用注释说明 `s.see` 里有什么、可以从哪里改起。
6. **成绩够稳**。`sets.K` 调到校验脚本不再提醒"换一批数据最好的规则会变"为止。
7. 一周七道题题材错开：定价、存货、最优停止、拍卖出价、期权行权、执行和做市、多臂老虎机、估计和检验、排队、博弈都可以，不要连着几天是同一类。以前出过的题（看 `q/` 里的 `id` 和题面）不要换个皮再出一遍。
8. 场景是虚构的、中性的，不涉及真实的人和公司，不构成投资建议。

## 校验脚本

下面的命令都在 `strategy-lab/` 这一层运行，只需要 Node，不用安装任何东西。

```sh
node daily/check.js daily/q/2026-10-21.json …   # 核对这几道题：格式、跑得通、可复现、分得出高下、够快
node daily/check.js --all                        # 核对 q/ 里的每一道题，以及 index.json、代号有没有重复
node daily/check.js --index                      # 按 q/ 里现有的文件重写 index.json
node daily/check.js --review 文件…               # 核对之后印出一份给人审的 Markdown：中英文题面、基准规则的成绩、第一局的前几回合、裁判的代码
node daily/check.js --try=规则.js --p='{"r":8}' 文件…   # 把一条自己写的规则放到这几道题上试：公开的几组上的成绩，以及换几批数据后比最好的基准规则好多少
```

有一处不通过，退出码就是 1。"提醒"不影响退出码，但要逐条看过：要么改掉，要么在送审的时候说明为什么可以留着。`node test/quest.test.js` 会把 `q/` 里的每一道题再核对一遍，加题之后也要跑通。

## 每周出题和送审的流程

每周出下一批七道题，开一个 PR，由仓库的主人审过之后合并。出题的一方（不管是人还是定时运行的 Claude）照下面做，不要自己合并，也不要直接往 `main` 上推。

1. 取最新的 `main`。先看有没有还开着的出题 PR（分支名以 `daily-` 开头）：
   - 有，而且里面的日子都还没开始：这一周不再出新的，说明"上一批还在等合并"就结束。
   - 有，但里面有的日子已经开始或者过去了：就在那个 PR 上改。把已经开始的日子的文件删掉，在后面补上新的日子，让它重新是"从明天（UTC）起连着七天"，再照第 3 到第 6 步核对、更新 PR 的正文。
   - 没有：从 `origin/main` 开一个新分支 `daily-第一天的日期`。
2. 定日期：从 `index.json` 里最后一天的后一天起，连着七天。要是算出来的第一天不晚于今天（UTC），说明中间断过：改成从明天（UTC）起连着七天。已经有文件的日子不要动。
3. 读一遍 `q/` 里已有的题，避开出过的题材，定下这七天各出什么。每道题照上一节的标准写成 `q/日期.json`。
4. 每道题都要：`node daily/check.js 文件` 通过；用 `--try` 确认基准规则上面留有余地；把题面从头到尾和裁判的代码对一遍。
5. `node daily/check.js --index`，再 `node daily/check.js --all` 和 `node test/quest.test.js`，都要通过。
6. 提交（只改 `strategy-lab/daily/` 里的文件），推上去，开 PR。标题写清楚是哪七天；正文依次是：
   - 一张表：日期、题目、一句话、基准规则里最好的成绩、出题时试过的更强的规则比它好多少；
   - 要在什么时候之前合并：第一天的 UTC 0 点，同时写出北京时间和加州时间；
   - 校验脚本留下的提醒，以及为什么可以留着；
   - `node daily/check.js --review 这七个文件` 印出来的全文。超过 6 万字时，正文放前面几项，全文分成几条评论贴在 PR 下面。

### 审题的人看什么

- 题面读一遍：不看代码能不能动手写规则？有没有哪句话有两种读法？
- 正文表格里的数和题面说的对不对得上；"基准规则的第一局"那张表里，规则看到的东西是不是题面说的那样。
- 想改：直接在 PR 的分支上改 JSON，或者在 PR 里留言。改完跑一遍 `node daily/check.js 文件`。
- 想去掉某一天：删掉那个文件，跑 `node daily/check.js --index`。那一天页面会重温一道旧题。
- **要在第一天开始之前合并**。晚了的话，先把已经开始的日子的文件删掉（并重写 `index.json`）再合并。

## 防得了什么，防不了什么

- 结算的数据在截止之前没有人知道，所以去凑公开那几组的数没有用。这一条靠的是 drand；页面拿到随机数以后会核对它和签名对得上（随机数应该是签名的 SHA-256），但不验证签名本身。
- 交上来的代码是公开的 Issue，截止之前别人看得到，可以照抄；同分的时候先交的排前面。
- 截止之后改 Issue 的人拦不住，只能标出来："截止后有变动"的意思是那条 Issue 在截止之后被动过，可能是改了代码，也可能只是有人留言，页面分不出来。
- 下一批题合并的时候就公开了（仓库是公开的），想提前看题的人看得到。
- 每个人的规则各自和裁判在一个隔离环境里跑，碰不到页面、碰不到别人的规则，也连不了网；但规则和裁判在同一个线程里，没法完全隔绝。所以这个榜图个乐，不要拿它来分奖品。
